# Vacation planner: design

Status: draft 1, 2026-10-21. Implements [REQUIREMENTS.md](REQUIREMENTS.md) (draft 2); requirement IDs refer to that file.
Guiding rule: **keep long-term maintenance low.** Few dependencies, a stable framework, and domain logic that doesn't depend on the UI.

## 1. Stack

| Concern | Choice | Why |
|---|---|---|
| UI | React + TypeScript (strict) | The component API (function components and hooks) hasn't changed since 2019; largest pool of help. Used client-side only, so the server-side features where React's churn happens don't apply. |
| Build | Vite | The standard way to build a static app; the output is plain files for GitHub Pages (`base: '/vacation_planner/'`). |
| Unit tests | Vitest | Same config as Vite. Covers everything in `src/domain`. |
| End-to-end tests | Playwright | Runs the main user flows on every push, with `MemoryStorage` (§4.4) and a fake sign-in. |
| Styling | Plain CSS + CSS variables (one file per component) | No dependency; the theme is variables (CAL-4). |
| State | React built-ins (`useReducer` + context) | The app has one document per calendar, so it doesn't need a state library. |
| i18n | A typed dictionary of my own (`ro.ts`, `en.ts`) plus `Intl.DateTimeFormat` | Two languages don't justify i18next. A missing key fails type-checking. |
| Dates | `YYYY-MM-DD` strings + ~10 helper functions in UTC | All dates are whole days, so no date library or time-zone handling is needed. |
| Google | Google sign-in (GIS) script, Picker script (v2), Drive and Calendar REST called with `fetch` | No Google client library. |
| xlsx import | ExcelJS, loaded only when you import | Reads fills **and** borders (SheetJS community edition doesn't read styles). Not in the main bundle. |
| .ics | Generated by hand (~50 lines) | The format is simple; no library needed. |
| CI/CD | GitHub Actions: type-check, lint, unit tests, end-to-end tests, build, deploy to Pages | Deploys from `main`. |
| Updates | Dependabot, monthly, grouped (npm + actions) | One update PR a month. |
| Lint/format | oxlint (TypeScript, React, hooks, jsx-a11y, Vitest rules) + Prettier | typescript-eslint doesn't support TypeScript 7 yet; oxlint is one binary that doesn't depend on the TypeScript compiler. Prettier skips `*.md`. |

Runtime dependencies: `react`, `react-dom`, `exceljs` (lazy-loaded). Everything else is a dev dependency.

## 3. Document schema (v1)

One JSON document per Google account (§6.1 of the requirements). Every collection is a map from `id` to record; every record carries `Meta`.

```ts
type ISODate = string;            // "2027-06-03"
type Stamp   = string;            // ISO-8601 UTC timestamp
interface Meta { id: string; createdAt: Stamp; updatedAt: Stamp; deleted?: true }

interface PlanDoc {
  schemaVersion: 1;
  owner: { googleSub: string };               // stable Google account id
  people:               Record<string, Person>;
  leaveTypes:           Record<string, LeaveType>;
  blocks:               Record<string, Block>;
  holidayOverrides:     Record<string, HolidayOverride>;
  yearSettings:         Record<string, YearSettings>;      // id = `${personId}:${year}`
  adjustments:          Record<string, Adjustment>;
  dismissals:           Record<string, Dismissal>;
  following:            Record<string, Follow>;            // v2
  settings: { lang: 'ro' | 'en'; gcalCalendarId?: string; updatedAt: Stamp };
}

interface Person extends Meta { name: string; color: string; hasAccount: boolean }

interface LeaveType extends Meta {
  key?: 'annual' | 'floating' | 'excused' | 'swap' | 'closed' | 'special' | 'sick' | 'unpaid';  // built-ins
  name: { ro: string; en: string };
  color: string;
  budget: 'annual' | 'floating' | 'excused' | 'none';  // which balance it draws from (LT-2, LT-6)
  needsApproval: boolean;
  hidden?: boolean;
}

interface Block extends Meta {
  personId: string;
  typeId: string;
  start: ISODate; end: ISODate;               // inclusive
  status: 'idea' | 'planned' | 'approved';
  note?: string;
  swapFor?: ISODate;                          // swap day: which weekend holiday it replaces
  gcalEventId?: string;                       // IO-3
}

interface HolidayOverride extends Meta {
  date: ISODate; action: 'add' | 'remove' | 'rename';
  name?: { ro: string; en: string };
}

interface YearSettings extends Meta {
  personId: string; year: number;
  annualOpening: number;                      // BAL-1
  floatingQuota: number;                      // LT-6
  excusedQuota: number;                       // LT-6
  closedCountsAgainstAnnual: boolean;       // LT-3
}

interface Adjustment extends Meta { personId: string; year: number; date: ISODate; days: number; note: string }
interface Dismissal  extends Meta {                                     // SUG-3, DAY-4
  personId: string; kind: 'suggestion' | 'swap';
  start: ISODate; end: ISODate;               // swap: start = end = the weekend holiday
}
interface Follow     extends Meta { driveFileId: string; label: string }
```

- The per-year "counts against annual leave" setting for office-closed days (LT-3) lives in `YearSettings` and takes precedence over the type's `budget` for that year.
- Mapping to a future DynamoDB table: `PK = owner#person`, `SK = <collection>#<id>`, one item per record. `settings` becomes one item.

## 4. Storage

### 4.1 Interface (requirements §6.3)

```ts
interface Storage {
  listCalendars(): Promise<{ calendarId: string; ownerName: string; writable: boolean }[]>;
  load(calendarId: string): Promise<{ doc: PlanDoc; version: string }>;
  save(calendarId: string, doc: PlanDoc, baseVersion: string):
    Promise<{ ok: true; version: string } | { ok: false; conflict: true }>;
  create(initial: PlanDoc): Promise<{ calendarId: string; version: string }>;
}
```

### 4.2 DriveStorage

- **Finding the file:** `files.list` with `q = "appProperties has { key='app' and value='vacation_planner' } and 'me' in owners and trashed=false"`. With `drive.file` this only sees files the app created. If none is found → `create`.
- **Creating it:** a multipart upload of `vacation-planner.json` into the Drive root, with `appProperties: { app: 'vacation_planner' }`.
- **Version:** the Drive file's `version` field (a number that increases on every change).
- **Saving:**
  1. `files.get(fields=version)`.
  2. If it equals `baseVersion`, upload with `PATCH /upload/drive/v3/files/{id}?uploadType=media`.
  3. Otherwise return `conflict`, and the app reloads, merges (§4.3) and saves again.

  Drive v3 has no compare-and-swap, so there's a short race window between steps 1 and 2. Only the owner writes the file (requirements §6.4), so the worst case is two of my own devices saving within the same second. The newer save still contains the other device's records the next time it merges.
- **Saving cadence:** debounce 1.5 s after the last change; save on `visibilitychange` → hidden; status indicator shows saved / saving / error (NF-4).

### 4.3 Merge

`merge(local, remote)`: for every collection and every id in either document, keep the record with the later `updatedAt`. Deleted markers are records too, so a delete wins over an older edit. `settings` merges the same way as one record. This is a pure function, unit-tested.

### 4.4 MemoryStorage

Same interface, kept in memory and optionally seeded from a JSON file. Used:
- by Playwright (selected with build mode `VITE_STORAGE=memory`; that code path is removed from the production bundle);
- for the signed-out demo (AUTH-3): holidays only, read-only, nothing saved.

## 5. Google integration

### 5.1 Sign-in and tokens

- The GIS **token client** (`google.accounts.oauth2.initTokenClient`) asks for `openid email profile https://www.googleapis.com/auth/drive.file` at sign-in.
- The Google account id (`sub`) and display name come from the `userinfo` endpoint.
- `google/auth.ts` preloads the GIS script on page load, so the popup opens inside the click (browsers block popups that aren't). The session (token, expiry, user) is kept in `sessionStorage`: a reload in the same tab stays signed in until the token expires; a new tab or visit takes one click ("Continuă ca …", the last account is remembered in `localStorage` as a hint only). Never stored in `localStorage`.
- `ui/Root.tsx` owns sign-in: signed out → `MemoryStorage` demo; signed in → `DriveStorage(() => auth.accessToken())`, remounting `App` per account. `accessToken()` throws `AuthExpiredError` near expiry; `useDocument` then shows "reconnect", keeps the unsaved document in memory and saves after the click.
- Access tokens last about 1 h. Before one expires, the app asks again with `prompt: ''`, which normally happens without showing anything. If it fails, a "Sign in again" banner appears; unsaved changes stay in memory and are saved after signing in again.
- Calendar push (IO-3) calls `requestAccessToken` again with `include_granted_scopes: true` and adds `https://www.googleapis.com/auth/calendar.events`. This only happens the first time I click "push".

### 5.2 Calendar push (IO-3)

- Writes to my primary calendar by default, or to `settings.gcalCalendarId` if set (typed in Settings, because listing calendars needs a broader permission).
- Each block becomes one all-day event (`end` is exclusive, so the last day + 1), with `extendedProperties.private.blockId` set.
- Inserting or updating uses the stored `gcalEventId`; if the event was deleted in Calendar, it is created again. Deleting a block or moving it back to `idea` deletes the event.

### 5.3 Google Cloud setup (one time, by hand, with your existing Google account)

1. Create a Cloud project `vacation-planner`.
2. Enable the **Google Drive API** and the **Google Calendar API** (plus the **Google Picker API** in v2).
3. Configure the OAuth consent screen: user type *External*, app name and support e-mail, scopes as in §5.1, publishing status **In production** (AUTH-4).
4. Create an OAuth client ID of type *Web application*:
   - authorized JavaScript origins: `https://flriancu.github.io` and `http://localhost:5173`;
   - redirect URIs: none (the token model doesn't use them).
5. v2 only: create an API key restricted to the Picker API and the same origins.
6. Put the client ID in `src/config.ts`. It is not secret, so it's committed.

## 6. Domain algorithms

### 6.1 Holidays (DAY-1)

- **Orthodox Easter:** Meeus' Julian algorithm, then +13 days to convert to the Gregorian calendar (valid 1900–2099).
- **Moving holidays from Easter `E`:** Good Friday = E−2, Easter Monday = E+1, Rusalii = E+49 and E+50.
- **Fixed holidays:** as listed in DAY-1.
- **Overrides:** applied last. A date may have two holiday names (e.g. 1 Jun 2026 is both Children's Day and Rusalii Monday); it is shown once, with both names.

### 6.2 Day kind

`buildDays(doc, person, from, to)` (`calendar.ts`) gives each date:
- `base`: `holiday`, `weekend` or `work`, from the calendar alone;
- `blocks`: that person's live blocks covering the date, highest status first;
- `off`: `base ≠ work`, or covered by any `planned`/`approved` block (of any type);
- `anchor`: a holiday, or a `planned`/`approved` floating, swap or office-closed day.

Cost is always counted on `base = work` days. Being `off` is what lets a bridge pass through a day without paying for it.

### 6.3 Bridge candidates (SUG-1, SUG-7, SUG-8)

1. Find **anchors**: maximal runs of `off` days that contain at least one `anchor` day (§6.2).
2. For each anchor and each `l, r ≥ 0` with `1 ≤ l + r ≤ maxCost` (default 5): add `l` working days to the left and `r` to the right. After each added working day, extend over any free days next to it, so runs merge across weekends and neighbouring anchors.
3. Keep the range if both of its outer neighbours are `work` days. Remove duplicate ranges.
4. Compute `cost` = number of `work` days inside, `gain` = range length, `ratio` = gain ÷ cost, and the split (floating first, up to the available floating days).
5. Open swap reminders: run steps 1–4 twice, once with the Friday option and once with the Monday option. Label each candidate with the option it assumes.
6. Drop dismissed ranges and ranges that don't overlap the year. Sort by ratio (descending), then by gain (descending), then by date.

Planned or approved annual leave is `off`, so a candidate can extend leave that is already planned and only charges the new days. When such an idea is promoted (BLK-5), the UI offers to merge it into the existing block.

The number of candidates is small: ≤ ~25 anchors × 21 (l, r) pairs per year.

### 6.4 Plan proposal (SUG-4)

- **Break:** ≥ 3 consecutive free days. The existing planned and approved blocks, plus the free runs of ≥ 3 days that already exist, are fixed breaks.
- **Objective** (higher is better), where `w` is the slider in [0, 1]:

  `w · Σ gain_i − (1 − w) · k · Σ (gap_j / 30)²`

  `gap_j` are the stretches with no break between consecutive breaks, including from 1 Jan to the first break and from the last break to 31 Dec. Squaring the gaps penalises one long stretch more than several short ones, which is what "spread through the year" means. `k` is calibrated so that the default `w = 0.5` reproduces plans like my past ones (tuned locally, on private data only).
- **Solver:** dynamic programming over candidates sorted by start date, with state = (end of the last chosen break, budget used). The objective is additive per step, so this is exact. Size: ≲ 500 candidates × 30 budget × 365 days, which runs in milliseconds.
- **Constraints:** chosen candidates don't overlap each other or the fixed breaks; the total cost stays within available annual plus floating days.
- **Output:** a preview list. I accept all, some or none (SUG-5).

### 6.5 Balances (BAL-*, LT-6)

Accounting is **per working day**, not per block. Each `base = work` day of the year that a block covers is charged once, to its highest-status block, and to that block's budget (`blockBudget`, which applies LT-3). So overlapping ideas never double-count, and a block that crosses 31 Dec charges each year only for its own days.

Per person and year:
- `total = opening + Σ adjustments`;
- `used` = approved days before today;
- `reserved` = planned days, plus approved days from today on;
- `available = total − used − reserved`, which doesn't depend on `today`;
- `ideas` = days covered only by ideas;
- `ifIdeas = available − ideas`.

The floating and excused balances use the same formulas with their quotas and no adjustments; both expire on 31 Dec. Suggestions pay floating first, then excused, then annual (SUG-7). Types with no budget still get per-type totals (LT-5).

## 7. UI

- **Calendar (CAL-1..6):**
  - a CSS grid of week rows (7 day columns, plus a month column and a notes column on desktop);
  - month borders drawn per day cell from "is the first week of the month / first day of the month";
  - block outlines drawn per day cell: a cell draws an edge wherever its neighbour (the day before/after in the same week, or 7 days above/below) is outside the block. That traces the same outline as the old sheet's borders, with no measuring and no redraw on resize. Several blocks on one day are nested layers, 3 px apart;
  - months are a vertical band (2 rem; 1.6 rem on phone) in the first column, one per run of weeks whose Monday is in the month (`buildWeeks` gives `month` + `span`); the band is absolutely positioned and `span × --row-h` tall, so every row has the same fixed height;
  - no holiday-name column: names are in the cell's `title`/`aria-label` and the hint line; the calendar is capped at 46 rem wide, leaving room for side panels.
- **Selecting days (CAL-8):** pointer events (drag) on desktop; tap start, tap end on touch; Shift+arrow keys on keyboard (NF-6).
- **Layout (CAL-12), from a research pass over Material 3, Apple HIG, Fluent 2, NN/g and the big calendar apps:**
  - width classes (`ui/useLayout.ts`): compact < 600 px, medium < 1000 px, expanded ≥ 1000 px;
  - header (`ui/Header.tsx`), one row: title · ‹ year › · Azi, then at most three groups on the right (HIG toolbars, M3 app bars): save-status indicator (NN/g: a lasting state is an indicator, in one place), Setări menu (rarely changed preferences behind one click: HIG settings, NN/g progressive disclosure), account slot (same place signed in or out: "Conectează-te cu Google" ↔ initial avatar with a menu). Compact: no title, short labels, Setări inside the account menu (or a ⋯ menu signed out);
  - the header hides on scroll down and returns on scroll up (NN/g partially persistent header); `--header-offset` keeps the weekday row and the pane just under it; scrolls the app makes itself (Azi, first load) don't hide it;
  - expanded: a supporting pane on the right, 18 rem (M3 canonical "supporting pane"), sticky: legend (Carbon: a legend beside dense data when labels can't go in the cells), closable hint; later balance and suggestions. Medium: legend as one row above the calendar; compact: behind a "Legendă" disclosure;
  - one sign-in action, in the account slot: "Conectează-te cu Google", or "Continuă ca {first name}" for a returning browser (the hint keeps email + first name). Signed out, a thin strip under the header (GOV.UK phase banner) only explains the demo, plus a "Folosește alt cont" link for a returning browser;
  - header controls never wrap their labels (HIG, M3): they keep their size, the title truncates first, and the demo status shows "Demo" below 1200 px (full text in the tooltip);
  - menus (`ui/Menu.tsx`) are disclosures (button + panel with form controls), close on Escape and outside click;
  - phones use 44 px controls (HIG/M3 touch targets).
- **Visual encoding (CAL-4, CAL-6, CAL-11)**, checked against research (sources in the commit that introduced it):
  - *Status is ordered* (idea < planned < approved), so it is a **lightness ramp**: faint tint (9 %) → light fill → full accent. Lightness/value is the channel for ordered data (Bertin; Munzner's magnitude channels; ColorBrewer sequential schemes), and "lighter = less certain" was among the most intuitive cues in MacEachren et al. 2012. Hue is used only to separate "my leave" from "off anyway", never for order.
  - *Line style is the redundant cue*: dashed (idea) / solid (planned) / thick solid (approved). Dashing was the preferred uncertainty cue for lines (Boukhelifa et al. 2012) and gives a non-colour signal (WCAG 1.4.1).
  - *No patterns in cells*: high-contrast stripes near 3 cycles/degree cause pattern glare (Monger et al. 2015) and Google Calendar uses stripes for "declined"; a sparse dot pattern was tried next, but it made the day numbers harder to read (user feedback, 2026-10-21). Ideas are a faint tint instead.
  - *Two colours per scheme* (one tint, one accent): well under the 5–7 hues people track reliably (Healey 1996). The leave type lives in words (editor, tooltip).
  - *Past and out-of-year days mute only the number*: fading the cell would read as "less certain".
  - *Grid and month lines are muted, neutral* (Few: grid "just visible enough"); today is the only filled circle; holidays get a small dot lower in the cell.
  - *Contrast*: a script computes WCAG ratios for every scheme × mode (outlines ≥ 3:1 against plain and "off anyway" cells, numbers ≥ 4.5:1). The planned fill alone is ~1.4:1 by design; its solid outline carries the difference, as 1.4.11 allows.
  - *Schemes*: `<html data-scheme data-mode>`; tokens `--free`, `--leave`, `--leave-fg`, `--fill-planned` per scheme × mode in `theme.css`; `index.html` applies them before first paint.
- **Block description (CAL-7):** `ui/describe.ts` turns a block's cost and break into one sentence (plural forms from `i18n/plurals.ts`: "1 zi", "2 zile", "20 de zile"), worded by the budget it draws from; types that spend nothing only say how long the break is. Used by the editor and as the days' `title`.

## 10. Risks

| Risk | Mitigation |
|---|---|
| The GIS token refresh can be blocked by Safari's tracking protection or by pop-up blockers on phones | The "Sign in again" banner keeps unsaved changes in memory; test on iOS Safari in milestone 3. |
| Two of my devices save within the same second (§4.2) | Record-level merge on the next save; nothing is lost permanently. |
| A Romanian holiday law change | Per-year overrides (DAY-3); the fixed list lives in one file. |
| The plan proposal's weight `k` feels wrong | It's a single number, tuned locally against my past plans; the slider covers personal preference. |
